AI:

The honest truth first

You cannot reliably predict specific future changes. Anyone who tells you they can is lying or selling something. Even senior engineers guess wrong constantly. I guessed pricing would change because I've seen pricing change in every commercial system I've ever touched — but that's pattern recognition from experience, not foresight.

So the goal is not "predict the future." The goal is "make the cost of being wrong cheap."

That reframes the whole question. You stop asking "what will change?" and start asking "if this changes, how much code do I have to touch?"

The heuristics that actually work

These are the ones I use. They're not foresight — they're pattern recognition you can apply mechanically.

Heuristic 1: "Reasons to change" — the SRP lens, used as a question

For each class, list out loud the reasons it might be edited. If a class has multiple unrelated reasons, it's a smell.

For your Drink:

Edited if a new drink type is added → fine, that's its job
Edited if extras storage changes → fine, that's its job
Edited if pricing rules change → wait, why does adding a discount mean editing Drink?

That last bullet is the tell. It's a "this thing has its fingers in someone else's business" signal. You don't need to know what the pricing change will be. You just need to notice that pricing is a separate concern from "what is a drink."

The trick: list reasons for change, then look for ones that feel like they belong to a different concept. Those are the seams.

Heuristic 2: "Is this a fact or a policy?"

This one is gold. Memorize it.

A fact is something inherent to the thing. A latte is a latte. An espresso has espresso in it. These don't change based on business decisions.
A policy is a business decision. How much a latte costs. Whether there's a happy hour. Whether tax applies. Whether loyalty members get 10% off.

Facts belong on the data. Policies belong in separate classes (strategies, services, calculators).

In your design, DrinkType.LATTE having a name is a fact. DrinkType.LATTE having a price of $2.00 is a policy. You glued them together. That's why pricing is hard to change — the policy is welded to the fact.

You don't need to predict what the pricing policy will become. You just need to notice "this is a policy" and give it room to live somewhere else.

Apply this to anything:

"This user is named Alice" — fact.
"This user gets free shipping" — policy.
"This file is 4MB" — fact.
"This file should be compressed before upload" — policy.

If you can sort the world into facts and policies, you'll naturally pull policies out into their own classes without having to predict anything.

Heuristic 3: The "if/else on type" smell

The moment you find yourself writing:

java
if (drink.type() == LATTE) { ... }
else if (drink.type() == AMERICANO) { ... }

…stop. That's a signal that whatever you're computing is not an intrinsic property of the drink — it's a behavior that varies by type. Either it belongs on the type (polymorphism), or it belongs in a strategy class that knows how to handle each type.

You didn't write this in your code, but the moment a "discount only on hot drinks" rule shows up, you'll be tempted to. Recognize the smell early.

Heuristic 4: Verbs vs. nouns

Domain models tend to be nouns: Drink, Order, Customer. Operations on them are verbs: price, tax, discount, validate, notify, print.

Verbs that involve business rules deserve their own home. Not always a class — sometimes a method on a service. But "calculate price" is a verb that should be a thing, not a method buried inside Drink.

Quick test: can you say the verb without naming a specific noun? "Calculate price" stands alone. "Drink-itself" doesn't. That's a hint that pricing is its own concept.

Heuristic 5: "Would I delete this class if the rule changed?"

If the answer is "no, I'd just edit it," then the class is doing two things — being itself, and implementing the rule. Pull the rule out.

If the answer is "yes, I'd swap it for a different class entirely," good — you've already separated the rule.

In your design, if pricing rules changed, you wouldn't delete Drink. You'd edit Drink.getTotal(). That's the signal: pricing isn't part of Drink, it's a passenger riding on Drink.

The discipline that makes the heuristics actually work

Here's the part nobody tells juniors. The heuristics above don't matter if you skip this step:

Before you start coding, write down 3–5 sentences describing what each class is responsible for. Not what it does mechanically — what it's for.

Try it for your design:

Drink: "Represents a configurable drink — its base type and the extras a customer asked for."
Order: "Represents a customer's set of drinks and where the order is in its lifecycle."
DrinkType: "Represents one of the drinks the shop sells."
DrinkExtras: "Represents one of the extras the shop offers."

Now reread those four sentences and ask: where does "compute the total price" belong?

It doesn't fit naturally in any of them. None of those sentences mentioned money. Pricing is a fifth concern with no home — which is exactly why it ended up smeared across all four.

That's the discipline: if you write the class purposes first and an operation doesn't fit any of them, that operation needs its own home. No prediction required. The misfit reveals itself.

AI:

SRP and OCP are talking about different things

SRP — Single Responsibility Principle
Question it answers: Should this method exist on this class at all?
Test: "Does this method serve the same reason-to-change as the rest of the class?"

OCP — Open/Closed Principle
Question it answers: When requirements change, can I extend behavior without editing existing code?
Test: "To add this new feature, did I have to crack open a working, tested class?"

They are not the same question. A change can violate one without violating the other. Let me show you all four cases.

Case 1: Adding a method that belongs — fine on both fronts

You have a Drink class. You add Drink.containsCaffeine() because the espresso bar wants a caffeine warning.

SRP? Fine. "Knowing facts about itself" is what Drink is for. Caffeine status is a fact about a drink.
OCP? Technically you edited Drink, but you added a new capability, not a new branch in existing logic. Adding genuinely new methods to a class is normal evolution. OCP isn't a vow of celibacy against ever touching old code — it's a warning against editing old logic to support new variants of an existing concept.
Verdict: Add the method. No principle violated.
Case 2: Adding a method that doesn't belong — SRP violation

You have a Drink class. You add Drink.sendToKitchen() that calls a kitchen printer.

SRP? Violated. Drink is about being a drink, not about communicating with kitchen hardware. The reason Drink would change ("we added a new drink type") is unrelated to the reason sendToKitchen would change ("we switched printer vendors"). Two reasons to change = two responsibilities.
OCP? Not directly. You added new behavior. But you put it in the wrong home, which makes future OCP violations more likely.
Verdict: Method belongs on a different class. KitchenDispatcher.send(drink) or similar.
Case 3: Editing an existing method to handle a new case — OCP violation

You have Drink.getTotal() summing base + extras. A new requirement says "espressos are exempt from extra-shot pricing." You edit getTotal:

java
public BigDecimal getTotal() {
    BigDecimal sum = drinkType.getPrice();
    for (var extra : extras) {
        if (drinkType == ESPRESSO && extra == EXTRA_SHOT) continue;  // <-- new
        sum = sum.add(extra.getPrice());
    }
    return sum;
}
SRP? Arguable. Pricing was already on Drink, so this is "more of the same."
OCP? Violated. You modified existing, working logic to handle a new variant. Now getTotal is a magnet for every weird pricing edge case the shop dreams up. Six months later it's 80 lines of if/else and nobody understands it.
Verdict: This is the smell I keep warning about. The fix is to lift pricing out so each rule lives in its own home.
Case 4: Adding a method that pulls in a whole new responsibility — SRP and OCP both

You add Drink.applyHappyHourDiscount(LocalTime now) directly on Drink.

SRP? Violated. Drink now needs to know about time, business hours, and discount rules. None of those are "what is a drink."
OCP? Violated next. Tomorrow when student discount lands, you'll add Drink.applyStudentDiscount. Then applyMemberDiscount. The class becomes a discount museum.
Verdict: Don't add it. This belongs in a PriceCalculator or DiscountPolicy.
So the actual rule

Adding a method is fine when the method serves the same purpose as the class. It violates SRP when the method drags in a new responsibility. It violates OCP when, instead of adding a method, you're editing an existing method to absorb a new variant of behavior.

Three quick litmus tests you can apply on the spot:

The "reason to change" test (SRP). Could this new method change for reasons unrelated to why the rest of the class changes? If yes, wrong home.
The "switch on type" test (OCP). Am I about to write if (someType == X) or switch (someType) inside an existing method? If yes, you're forcing existing code to know about a new variant — push the variant-specific behavior somewhere it can live independently.
The "magnet" test. Can I imagine this method becoming a graveyard for every future special case? If yes, the method itself is the problem, not the addition you're about to make.
